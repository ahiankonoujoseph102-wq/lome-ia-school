Ce fichier donne à Claude le contexte du projet. Le lire avant toute modification.

## La personne qui porte le projet

- N'est **pas développeuse ou développeur** et travaille **uniquement depuis un téléphone**, via Claude Code sur le web.
- **Langue (règle absolue)** : toutes les réponses, tous les résumés et tous les messages destinés à Joseph (porteur du projet) sont rédigés **en français simple, sans exception** : réponses dans la conversation, résumés de fin d'étape, commentaires et descriptions de pull request, messages d'aperçu. Jamais d'anglais, même pour une réponse courte.
- Toujours expliquer simplement, en français, ce qui a été fait et pourquoi.
- Signaler clairement tout ce qu'elle doit faire elle-même : créer un compte, fournir une clé d'API, cliquer sur un bouton dans un tableau de bord, valider une pull request…
- Aucune commande ne peut être lancée de son côté sur un ordinateur : Claude exécute, vérifie et pousse tout.
- Finir chaque étape par un résumé : fait / échoué / à faire de son côté.

## Le produit

Plateforme de vente et de suivi de formations en intelligence artificielle, basée à Lomé (Togo).

- **Achat puis accès immédiat** : l'élève paie et accède tout de suite à la formation.
- **Trois formats** :
  - enregistré : vidéos intégrées (YouTube aujourd'hui) ;
  - en direct : sessions Google Meet ;
  - en présentiel : à Lomé.
- **Groupe de discussion par formation**, réservé aux acheteurs, dans le style de WhatsApp : texte, images, captures d'écran, notes vocales, vidéos courtes, fichiers. Il doit être très professionnel et confortable à utiliser, sur mobile d'abord.
- **Affiliation** : un élève gagne 10 % de chaque vente faite via son lien. Retrait par Mobile Money. Au début, les retraits sont validés manuellement par l'admin.
- **Consultation gratuite** sur réservation.
- **Tableau de bord admin** complet.
- **Paiement** : aujourd'hui, Mobile Money **manuel avec preuve de paiement** (entreprise pas encore certifiée) ; FedaPay sera ajouté plus tard.
- **Exigences** : très professionnel, rapide, pensé mobile en priorité, conçu pour convertir les visiteurs en acheteurs.
- **Langue** : français. **Monnaie** : FCFA (XOF). **Fuseau horaire** : `Africa/Lome` (UTC+0, sans heure d'été).

## Stack technique (imposée)

- Laravel 13, PHP 8.4+ (starter kit officiel Livewire, authentification Fortify).
- Livewire 4 (composants monofichiers dans `resources/views/pages`, préfixe ⚡) + Flux UI + Alpine.js + Tailwind CSS 4 (Vite, via `vite-plus`).
- Base de données : SQLite en développement (`database/database.sqlite`), **MySQL en production**. Tout le code doit rester compatible MySQL.
- Temps réel du chat : Pusher, avec mise à jour régulière automatique (sans WebSocket) si Pusher est absent ou en panne.
- Paiement : Mobile Money manuel avec preuve (étape 4) ; FedaPay plus tard, derrière la notion de moyen de paiement (`App\Enums\PaymentGateway`).
- Hébergement final : Hostinger mutualisé avec SSH. **Pas de processus permanent** : files d'attente et tâches planifiées passent par cron (`schedule:run` chaque minute, `queue:work --stop-when-empty`).
- Fournisseur vidéo **interchangeable** : YouTube maintenant, Bunny.net plus tard.

## Règle sur les contenus (impérative)

- **Ne jamais inventer** de bonus, chiffres, durées, nombres de vidéos ou de leçons, résultats promis, avis, notes ou autres promesses.
- Tout contenu marketing qui n'a pas été fourni par la porteuse du projet doit lui être **signalé explicitement** (liste claire, formation par formation) avant d'être considéré comme validé.
- Les textes décrivent **ce que l'élève apprend à faire**, jamais un résultat garanti (revenus, clients, ventes, gain de temps, popularité). Le ton reste vendeur et dynamique.

## Conventions de code

- **Nommage** : code (classes, méthodes, variables, tables, colonnes) en anglais ; tout texte visible par l'utilisateur en français.
- **Textes d'interface** : le starter kit utilise des clés anglaises traduites dans `lang/fr.json`. Garder ce mécanisme pour ces écrans ; pour les nouveaux écrans, le français peut être écrit directement dans les vues Blade. Messages de validation : `lang/fr/validation.php`.
- **Style** : suivre le style existant ; `composer lint` (Pint) avant chaque commit.
- **Montants** : en FCFA, stockés en **entiers** (le XOF n'a pas de décimales). Jamais de float pour l'argent. Affichage : `25 000 FCFA`.
- **Dates** : l'application tourne en `Africa/Lome`. Affichage en français (`translatedFormat`).
- **Compatibilité MySQL** : uniquement via les migrations et le query builder / Eloquent. Pas de SQL brut propre à SQLite. Attention aux types (`enum` natifs à éviter, préférer `string` + enum PHP), aux index uniques et aux clés étrangères.
- **Services externes** derrière une interface (ex. `VideoProvider` avec une implémentation `YouTubeVideoProvider`), choisis par la configuration, pour pouvoir changer de fournisseur sans toucher au reste du code.
- **Clés et secrets** uniquement dans `.env` (jamais commités) ; documenter chaque nouvelle variable dans `.env.example`.
- **Mobile d'abord** : concevoir chaque écran pour un petit écran, puis l'agrandir.
- **Tâches longues** (e-mails, traitements de médias) : en file d'attente (driver `database`), jamais pendant la requête.
- **Tests** : un test de fonctionnalité (PHPUnit) pour chaque parcours important (achat, accès, affiliation, retrait).

Les emplacements à remplir sont écrits entre crochets `[...]` et surlignés en doré sur le site (il n'en reste aucun aujourd'hui).

Trois types (exemples commentés dans le fichier) : `text`, `screenshot` (capture WhatsApp) et `video` (YouTube, lecteur chargé au clic). Lecture et filtrage des entrées incomplètes : `App\Support\Testimonials`, liens YouTube : `App\Support\YouTube`.
- **Réseaux sociaux** : un réseau dont le lien est vide dans `social` est masqué automatiquement.
- **Chiffres officiels** (fournis par la porteuse du projet) : plus de 1 000 personnes formées, école créée en 2023, horaires du lundi au samedi de 8 h à 20 h, consultation gratuite de 30 minutes. Ne jamais inventer de chiffres, notes ou avis.
- **Formations** : table `formations` (modèle `App\Models\Formation`), remplie par `database/seeders/FormationSeeder.php` (relançable sans doublon : `php artisan db:seed --class=FormationSeeder`). Catégories et formats : enums `App\Enums\FormationCategory` et `App\Enums\FormationFormat`. **Bonus** : liste par slug dans `config/site.php` (clé `bonuses`, toutes vides aujourd'hui ; section « Bonus » masquée si vide), lue par l'attribut `Formation::bonuses` ; la colonne `formations.bonuses` a été supprimée. Section « Inclus avec la formation » toujours affichée (clé `included`, dont l'accès au groupe privé).
- **Images** : logo dans `public/images/logo.svg` (ou `.png`), photo du formateur dans `public/images/formateur.jpg` (800 × 800 px, déjà en place ; texte alternatif `trainer.photo_alt`), images des formations dans `public/images/formations/` (nom du fichier à renseigner dans la colonne `image`), photos des témoignages dans `public/images/temoignages/`. Sans image, un visuel en dégradé est dessiné automatiquement.
- **Vues** : `resources/views/site/` (pages), `resources/views/components/site/` (composants), mise en page `resources/views/layouts/site.blade.php`.
- **CSS/JS du site vitrine**, séparés de l'espace membre pour rester légers : `resources/css/site.css` (Tailwind 4, couleurs `night`, `electric`, `gold`) et `resources/js/site.js` (Alpine.js : menu, filtre du catalogue, animations au défilement).
- **Design toujours sombre**, quel que soit le mode du téléphone : `<meta name="color-scheme" content="only dark">` dans le layout et, dans `site.css`, un bloc `:root` (`color-scheme: only dark`) / `body` (fond `night-950`, texte, police) placé **hors des `@layer` Tailwind** pour garder la priorité sur toute feuille de style extérieure. Ne pas remettre le fond de page dans `@layer base` seulement, et ne pas utiliser de variantes `dark:` sur le site vitrine.
- **Mode sombre forcé de Chrome** (fréquent sur Tecno, Infinix, Xiaomi, Samsung) : téléphone en mode sombre, Chrome respecte « only dark » ; téléphone en mode **clair** avec le forçage, Chrome recolore quand même (texte ou icône foncés éclaircis, fonds plus clairs qu'un gris 200/255 assombris, SVG retouchés ; les fonds foncés, les textes clairs et les images ne sont pas touchés). Parade : un script en tête du layout détecte ce cas (couleur système `canvas` = `rgb(18, 18, 18)` et téléphone en clair) et pose la classe `force-dark` sur `<html>` ; `site.css` compense alors, hors couches Tailwind : (1) couleur de thème **`veil`** (blanc, gris 198 en mode forcé) pour **tous** les voiles blancs translucides : écrire `bg-veil/5`, `border-veil/10`, `ring-veil/15`, `divide-veil/10`… et **jamais** `bg-white/…` (le test l'interdit) ; (2) double inversion (`filter: invert(1)` + fond aux couleurs inverses, listées dans `site.css`) pour les éléments à texte foncé sur fond clair : `.btn-gold`, `bg-gold-400 text-night-950`, `bg-emerald-500 text-night-950`, titre `.text-gradient`, pastilles `.method-dot` (couleur inverse fournie par `PaymentMethod::inverseColor()`), `.chat-file-icon`, `.chat-badge-trainer`, QR code `.qr-code` ; tout nouvel élément de ce type doit recevoir sa règle (attention : dans un conteneur à défilement horizontal, la double inversion ne fonctionne pas : pour un état « sélectionné », préférer texte clair sur fond doré translucide + contour doré, comme le sélecteur de créneaux) ; (3) visuel des formations dessiné en CSS (`.cover-art`), pas en SVG. **Règle de design pour tout nouvel élément d'interface** : privilégier d'emblée un style **stable face au mode sombre forcé** (fond foncé ou translucide, texte clair, contour coloré, comme le contour doré de sélection des créneaux ou l'alerte « Lien Google Meet non renseigné ») plutôt qu'un texte foncé sur fond clair qu'il faudrait ensuite compenser ; ne recourir à la double inversion qu'en dernier recours ; et **toujours vérifier** le nouvel élément par des captures dans les 4 combinaisons (clair/sombre × avec/sans forçage). Le reçu imprimable reste clair (`only light`, hors layout). Vérification : captures des 4 combinaisons (clair/sombre × avec/sans `--enable-features=WebContentsForceDark`) comparées pixel par pixel ; test `tests/Feature/Site/SiteColorSchemeTest.php`.
- **Bouton WhatsApp** : sur téléphone et tablette, il est dans l'en-tête (`site/partials/header.blade.php`) pour ne cacher aucun contenu ; le bouton flottant (`site/partials/whatsapp-button.blade.php`) n'apparaît que sur grand écran (`lg`).
- **Animations** : aucun contenu ne doit dépendre d'une animation pour être visible. `data-reveal` est visible au repos ; `site.js` ajoute `reveal-play` seulement aux éléments encore sous l'écran (désactivé si l'utilisateur préfère moins d'animations).
- **Images de partage** (Open Graph, 1200 × 630) générées en PHP (GD) par `App\Services\OgImageGenerator`, mises en cache dans `storage/framework/cache/og`. Routes `/og/site.png` et `/og/formations/{slug}.png`.
- **SEO** : titre, description, Open Graph et données structurées par page ; `/sitemap.xml` et `/robots.txt` (indexation bloquée hors production).
- Le bouton « Acheter maintenant » mène au récapitulatif de commande `/commande/{slug}`, où se fait le paiement Mobile Money (voir « Paiements »). La consultation gratuite se réserve en ligne sur `/consultation-gratuite` (voir « Consultation gratuite »).

## Comptes, rôles et accès

- **Inscription** : nom, numéro WhatsApp (obligatoire, unique, stocké au format international complet via `App\Support\PhoneNumber`, règle `App\Rules\WhatsAppNumber`). `PhoneNumber::PLANS` donne, par pays, la longueur du numéro et si le 0 initial est un simple préfixe national (France, Ghana, Nigeria…) ; en Afrique de l'Ouest il fait généralement partie du numéro et n'est **jamais retiré** (Bénin : 10 chiffres commençant par 01, un ancien numéro à 8 chiffres reçoit 01 devant ; Burkina Faso : 8 chiffres, ex. +226 07 27 63 81). Même règle pour le profil et le numéro payeur des paiements. Réparer des numéros enregistrés par l'ancienne normalisation (0 perdu) : `php artisan app:fix-phone-numbers [--dry-run]` (ne crée jamais de doublon), e-mail, mot de passe (pas de confirmation, bouton « Afficher »), case facultative **non cochée par défaut** « Je souhaite être informé(e) des nouvelles formations » (colonne `users.wants_newsletter`, modifiable dans le profil, composant `x-site.newsletter-checkbox`). N'envoyer d'annonces qu'aux élèves dont `wants_newsletter` est vrai. Pages d'authentification au design du site : `resources/views/site/auth/`.
- **Rôles** : `App\Enums\UserRole` (élève, modérateur, admin), colonne `users.role` non modifiable par formulaire. Créer ou promouvoir un admin : `php artisan app:make-admin email@exemple.com` (le mot de passe est demandé au clavier, jamais écrit dans le code). Zone admin protégée par le middleware `admin` et la permission `access-admin` (pages à l'étape 10, préfixe `/admin`).
- **Inscriptions aux formations** : table `enrollments` (élève, formation, `source` = `purchase` ou `admin`, `granted_at`). Règle d'accès au contenu : `App\Policies\FormationPolicy::access` (élève inscrit ou admin), à utiliser avec `can:access,formation` aux étapes 5 et 6. Donner ou retirer un accès : `php artisan app:grant-access email slug [--revoke]`.
- **Retour après connexion** : un visiteur qui passe par `/commande/{slug}` y revient automatiquement après inscription ou connexion (URL « intended » de la session).
- **Espace élève** « Mon espace » (`/mon-espace`) : vues `resources/views/site/student/`, variante `student` du layout du site (barre de navigation en bas sur téléphone). Profil et photo : `/mon-espace/profil` (photo recadrée en 320 × 320 par `App\Services\AvatarProcessor`, disque `public` : nécessite `php artisan storage:link` sur le serveur). Sécurité du compte (mot de passe, double authentification, passkeys) : `/mon-espace/securite` (`App\Http\Controllers\Student\SecurityController`), via les routes de Fortify et de Laravel Passkeys.
- **E-mails** : `App\Mail\WelcomeMail` (file d'attente) envoyé à l'inscription par `App\Listeners\SendWelcomeEmail`. En local, `MAIL_MAILER=log` : les e-mails sont écrits dans `storage/logs/laravel.log` quand la file est traitée (`php artisan queue:work --stop-when-empty`).

## Paiements (étape 4 : Mobile Money manuel avec preuve)

- **Configuration** (`config/site.php`, clé `payments`) : seuil de vérification (`$verificationThreshold` en haut du fichier, 50 000 FCFA), pays (Togo, Burkina Faso, Bénin, avec la mention du représentant), numéros Mobile Money (nom exact, numéro, bénéficiaire, couleur de pastille, `enabled`), étapes affichées, mention des frais, taille maximale de la capture, e-mail de l'admin. Lecture : `App\Payments\PaymentMethods` / `PaymentMethod`.
- **Parcours** : `/commande/{slug}` (choix du pays puis du moyen, numéro + « Copier », bénéficiaire, montant exact, étapes) puis formulaire de preuve (`POST /commande/{slug}/paiement`, `App\Http\Requests\StorePaymentProofRequest`). Traitement : `App\Actions\Payments\SubmitManualPayment`.
- **Contrôles automatiques** : formation déjà possédée (accès ou achat provisoire/validé), un seul paiement non vérifié à la fois par élève, identifiant de transaction jamais utilisé (normalisé : sans espaces, en majuscules, index unique), même capture jamais envoyée (empreinte SHA-256 du fichier envoyé, index unique). Échec : message clair, aucun accès, capture supprimée.
- **Accès** : prix < seuil → statut « accès provisoire » et accès immédiat ; prix ≥ seuil → « en attente de validation », aucun accès avant validation. Le délai affiché est celui de `payments.verification_hours`. `Formation::needsPaymentVerification()` et `Formation::guarantees()` adaptent les textes des pages formation.
- **Table `purchases`** (`App\Models\Purchase`, statuts `App\Enums\PurchaseStatus` : provisoire, en attente, validé, refusé, remboursé) : élève, formation, montant, passerelle (`gateway`), moyen de paiement (clé + copie du nom, du numéro et du bénéficiaire), pays, numéro payeur, nom de l'expéditeur, identifiant de transaction, capture (`proof_path`), empreinte, admin et date de vérification, motif du refus. Prévus vides : `affiliate_code` (étape 8), `discount_amount`, `gateway_reference` (FedaPay). `enrollments.purchase_id` relie l'accès à l'achat qui l'a ouvert (un accès donné par l'admin n'est jamais retiré par un refus).
- **Captures** : disque privé `payment_proofs` (`storage/app/private/payment-proofs`, jamais public), réduites à 1600 px et compressées en JPEG (`App\Payments\ProofImageProcessor`). Lecture uniquement par l'élève propriétaire ou l'admin (`App\Policies\PurchasePolicy`, `App\Http\Controllers\PurchaseProofController`, en-têtes `no-store`). À sauvegarder avec la base (étape 11).
- **Cycle de vie** : `App\Services\PurchaseManager` (commun à tous les moyens de paiement) : `grantAccess`, `validate`, `reject` (retire l'accès immédiatement, option de blocage du compte), `refund`, `block`/`unblock`. Compte bloqué (`users.blocked_at`) : connexion refusée (`FortifyServiceProvider`) et session fermée (middleware `LogoutBlockedUser`).
- **Événements** : `FormationAccessGranted` (branché : ajout au groupe), `FormationAccessRevoked` (branché : retrait du groupe), `AccountBlocked` / `AccountUnblocked` (branchés : retrait de tous les groupes / retour), `PaymentValidated` (étape 8 : commission d'affiliation **uniquement ici**, jamais sur un accès provisoire), `PaymentRejected`, `PaymentSubmitted`.
- **E-mails** (file d'attente, dans le journal en local) : `PaymentProofReceivedMail` (élève), `NewPaymentToVerifyMail` (admin, adresse `payments.admin_email`), `PaymentValidatedMail` (avec lien vers le reçu), `PaymentRejectedMail` (avec le motif). Gabarit commun : `resources/views/emails/layout.blade.php`.
- **Élève** : « Mes achats » `/mon-espace/achats` (statuts), suivi d'un achat `/mon-espace/achats/{id}` (sert de confirmation), reçu imprimable `/mon-espace/achats/{id}/recu` (paiement validé uniquement ; page autonome claire, `color-scheme: only light`). Mention « accès provisoire » sur les formations concernées.
- **Admin** : « Paiements à vérifier » `/admin/paiements` (provisoires et en attente, plus récents en haut, capture en grand, détails, signaux d'alerte `App\Services\PaymentAlerts`, rappel « À confirmer avec le représentant » pour le Burkina Faso et le Bénin, boutons Valider / Refuser avec motif et blocage du compte, dernières décisions). Compteur dans le menu admin (`site/partials/admin-payments-link.blade.php`).
- **Ajouter FedaPay plus tard** : nouveau cas dans `PaymentGateway`, parcours propre (redirection + webhook), référence dans `gateway_reference`, puis `PurchaseManager::validate()` à la confirmation. Les clés vont dans `.env`, jamais dans le code.

## Cours : contenu et lecteur (étape 5)

- **Structure** : formation → modules (`course_modules`, ordonnés par `position`) → leçons (`lessons` : titre, description courte, vidéo principale `video_provider` + `video_id`, vidéo de secours facultative `backup_video_provider` + `backup_video_id`, durée en secondes, `is_preview` = aperçu gratuit, `is_published`, `position`) → ressources (`lesson_resources` : soit un fichier envoyé, `path` sur le disque privé `lesson_resources` = `storage/app/private/lesson-resources`, soit un lien Google Drive, `url`). Modèles `CourseModule`, `Lesson`, `LessonResource`, `LessonView`. **Aucun module ni aucune leçon inventés** : le contenu est saisi par l'admin (l'ancien programme rédigé dans le seeder a été supprimé, colonne `curriculum` retirée).
- **Fournisseurs vidéo interchangeables** : interface `App\Contracts\VideoProvider` (reconnaissance du lien, message d'erreur précis, aide et rappel pour l'admin, lecteur intégré, lien de partage), implémentations `App\Video\YouTubeVideoProvider` (lecteur youtube-nocookie avec `rel=0`, `iv_load_policy=3`, `playsinline=1`, plein écran autorisé) et `App\Video\GoogleDriveVideoProvider` (lecteur d'aperçu Drive `/file/d/{id}/preview`), déclarées dans `config/video.php` (l'ordre = celui des champs de l'écran admin ; `VIDEO_PROVIDER` = fournisseur par défaut), accès via `App\Video\VideoProviders`. Pour Bunny.net : une classe de plus, déclarée dans `config/video.php`, et sa reconnaissance de lien dans `videoSources` de `site.js` (aperçu à la saisie). Liens YouTube reconnus (`App\Support\YouTube::id`) : watch, youtu.be, m.youtube, shorts, live, embed, v/. Liens Drive reconnus (`App\Support\GoogleDrive::fileId`) : file/d/…/view ou /preview, file/u/0/d/…, open?id=, uc?id=, docs.google.com/file/d/…, drive.usercontent ; un lien de dossier est refusé avec un message précis. Le fichier Drive doit être partagé en « Tous les utilisateurs disposant du lien » (rappel affiché à l'admin). Comme pour une vidéo YouTube non répertoriée, quelqu'un qui obtient le lien direct peut la voir : la protection porte sur les pages du site.
- **Admin « Contenu des formations »** (`/admin/contenu`, contrôleurs `Admin\CourseContentController` et `Admin\LessonController`, validation `App\Http\Requests\LessonRequest`) : choix de la formation, modules (ajouter, renommer, monter/descendre, supprimer avec confirmation), leçons (ajouter, modifier, changer de module, monter/descendre via `App\Courses\Positions`, publier/dépublier, supprimer), aperçu de la vidéo pendant la saisie du lien (Alpine `lessonVideoPreview` dans `site.js`), un champ de lien par fournisseur (YouTube, Google Drive) avec choix du « lecteur principal », l'autre lien devenant le lecteur de secours ; fichiers (PDF, images, Office, ZIP, TXT, CSV, MP3 ; 20 Mo par fichier, 10 par envoi : vérifier `upload_max_filesize` et `post_max_size` dans le PHP de Hostinger) ou lien Google Drive (nom + lien, vérifié : drive.google.com ou docs.google.com en https).
- **Lecteur** : `/formations/{slug}/lecons/{id}` (`App\Http\Controllers\LessonController`) pour les élèves ayant accès (y compris provisoire) et pour tous les visiteurs sur une leçon « aperçu gratuit » publiée ; téléchargement des ressources `/formations/{slug}/lecons/{id}/fichiers/{id}` avec les mêmes droits (`App\Policies\LessonPolicy`, en-têtes `no-store`) ; bouton « Marquer comme terminée » (`POST …/terminee`, réservé aux élèves inscrits). Si la leçon a une vidéo de secours, bouton « Lecteur de secours » (`?lecteur=secours`, mêmes droits d'accès). Les liens Drive des ressources ne sont jamais écrits dans la page : ils s'ouvrent par une redirection réservée aux élèves ayant accès à la formation (jamais aux visiteurs d'un aperçu gratuit). Une leçon non publiée n'est visible que par l'admin. Page d'une formation achetée `/mon-espace/formations/{slug}` : progression en %, « Reprendre où j'en étais », programme avec l'état de chaque leçon.
- **Suivi** (`lesson_views`, service `App\Courses\CourseProgress`) : première consultation (jamais modifiée), dernière consultation, leçon terminée. `startedAt()` donne la date de la première leçon consultée d'une formation : affichée à l'admin sur « Paiements à vérifier » (« Formation commencée : oui / non ») pour la règle de remboursement sous 48 h. Les consultations d'admin et d'aperçus gratuits ne sont pas enregistrées.
- **Programme public** : `Formation::publicCurriculum()` (modules ayant au moins une leçon publiée), nombre réel de leçons, durée totale seulement si toutes les leçons publiées ont une durée (`totalDurationSeconds()`). Section masquée s'il n'y a aucune leçon publiée ; même règle pour le récapitulatif de commande.

## Groupes de discussion (étape 6)

- **Un groupe par formation** (`chat_groups`, modèle `ChatGroup`, créé automatiquement à la création d'une formation ; `ChatGroup::forFormation()`). Membres : `chat_group_members` (`ChatGroupMember` : date d'entrée, retrait + motif `App\Enums\ChatRemovalReason`, sourdine `muted_until`, dernier message lu, dernier message annoncé par e-mail, notifications coupées pour ce groupe, règles vues). Un membre retiré garde sa ligne : une **exclusion** n'est jamais annulée par un nouvel accès.
- **Adhésion** (`App\Chat\GroupMembership`) branchée sur les événements : `FormationAccessGranted` → ajout (accès provisoire ou validé), `FormationAccessRevoked` → retrait immédiat (refus, remboursement, `app:grant-access --revoke`), `AccountBlocked` / `AccountUnblocked` (émis par `PurchaseManager::block/unblock`) → retrait de tous les groupes / retour. Nouveau membre : l'historique est visible mais ne compte pas comme non lu.
- **Rôles** : `UserRole::Moderator` en plus d'élève et admin. Admin (badge « Formateur ») et modérateurs (badge « Équipe ») sont membres de tous les groupes (`isStaff()`, permission `moderate-chat`). L'admin donne ou retire le rôle à un compte existant : `/admin/equipe`. Pas de messages privés : uniquement les groupes.
- **Confidentialité** : les membres ne voient que le nom, la photo et le badge ; jamais le numéro ni l'e-mail (vérifié par les tests). Réponses du chat en `Cache-Control: no-store, private` (middleware `no-store`).

Fichiers sur le disque privé `chat_media` (`storage/app/private/chat`), servis uniquement aux membres par `Chat\AttachmentController` (lecture par morceaux pour les vidéos sur iPhone). Réponse (citation), suppression (le message devient « Ce message a été supprimé », texte et fichier effacés), liens cliquables et échappés (`App\Chat\MessageText`), séparateurs par jour (`App\Chat\ChatDates`), messages regroupés (`App\Chat\MessageGrouping`), non-lus (`App\Chat\UnreadCounter`, onglet « Groupes » de la barre du bas), ouverture au premier non-lu, historique chargé en remontant (`App\Chat\ConversationLoader`), signalement (`chat_message_reports`).
- **Temps réel** : `App\Chat\ChatRealtime` diffuse **immédiatement** (`ShouldBroadcastNow`, jamais par la file) l'événement `App\Events\Chat\ChatGroupChanged` sur le canal privé `chat.group.{id}` (`routes/channels.php`). Il ne contient aucun contenu : le navigateur recharge les nouveautés avec ses propres droits (`GET …/messages?after=&since=`). Sans clés Pusher, ou si Pusher échoue, le message est enregistré quand même et le navigateur se met à jour toutes les 4 s (30 s quand Pusher est connecté). Code du navigateur : `resources/js/chat.js` (chargé seulement sur la page d'un groupe ; `laravel-echo` et `pusher-js` chargés seulement si Pusher est configuré).
- **Modération** (admin et modérateurs, `Chat\ModerationController`, `Chat\ReportController`) : supprimer n'importe quel message, épingler (5 au maximum, affichés en haut du groupe), sourdine (durées dans `config/chat.php`), exclusion et réintégration (page « Membres du groupe »), mode « annonces seulement », page « Messages signalés » `/moderation/signalements`. Règles du groupe affichées à l'entrée et après chaque modification, modifiables par l'admin (`/admin/groupes`, avec « appliquer à tous les groupes » ; texte par défaut dans `config/chat.php`).
- **Admin** « Groupes de discussion » `/admin/groupes` : membres, messages, activité de la semaine, espace disque des fichiers (total et par groupe), mode annonces, règles.
- **Notifications** : sur téléphone (Web Push, interface `App\Contracts\PushSender`, `App\Push\WebPushSender` avec les clés VAPID de `.env`, sinon `NullPushSender`), envoyées par la file d'attente (`App\Jobs\SendChatPushNotifications`) aux membres qui ne lisent pas déjà le groupe ; abonnements `push_subscriptions`. Réglages `/mon-espace/notifications` (téléphone, e-mail récapitulatif, groupes coupés) avec l'explication iPhone (ajout à l'écran d'accueil, iOS 16.4+). E-mail récapitulatif `App\Mail\ChatDigestMail` par `php artisan app:send-chat-digests` (planifié chaque jour à 18 h, heure de Lomé ; au plus un par jour, seulement s'il y a des non-lus pas encore annoncés).

Le message reste avec la mention « Fichier expiré » (colonne `chat_messages.attachment_expired_at`, `ChatMessage::isExpired()`). Les textes, images et documents sont conservés. Annoncé dans les règles des groupes et la politique de confidentialité.

## Sessions ponctuelles en direct et en présentiel (étape 7)

- **Principe** : toutes les formations sont enregistrées ; l'admin ou un modérateur annonce de temps en temps une session pour une formation. **Aucune session ni date n'est inventée** : tout est créé depuis l'écran « Sessions » (`/admin/sessions`, permission `manage-sessions` = admin et modérateurs).
- **Modèles** : `LiveSession` (formation, type `App\Enums\SessionFormat` en direct / présentiel, titre et description facultatifs, `starts_at` à l'heure de Lomé, `duration_minutes`, `ends_at` calculé, lien Google Meet vérifié par `App\Support\GoogleMeet`, lieu pré-rempli, places, tarif `App\Enums\SessionPriceType` inclus / supplément en FCFA, annulation, annonce du groupe, rappels envoyés) et `LiveSessionRegistration` (statut `App\Enums\RegistrationStatus` : inscrit, place réservée, liste d'attente, annulée ; paiement, présence). Réglages : `config/live_sessions.php` (lieu par défaut, délai d'annulation 24 h, bouton « Rejoindre » 15 min avant, rappels veille et 1 h, délai de 24 h pour payer un supplément, heure du Bénin).
- **Qui voit quoi** (`App\Policies\LiveSessionPolicy`) : élèves ayant accès à la formation (accès provisoire compris) et équipe. Le lien Google Meet n'est **jamais** affiché aux non-acheteurs ni sur les pages publiques (page formation « Prochaine session » et accueil « Prochaines sessions » via `x-site.session-summary`, sans lien).
- **Présentiel** (`App\LiveSessions\SessionRegistrar`) : inscription obligatoire, places limitées (verrou pour ne jamais dépasser), liste d'attente ; une place libérée va automatiquement à la première personne en attente, prévenue par e-mail et notification. Annulation par l'élève jusqu'au délai. Accès retiré ou compte bloqué → inscriptions annulées (écouteur `CancelSessionRegistrationsOnAccessLoss`).
- **Supplément** : même paiement Mobile Money avec preuve que les formations (`SubmitManualPayment` avec `$session`, `purchases.live_session_id`, mêmes contrôles, même seuil, même page « Paiements à vérifier », reçu dans « Mes achats », libellés `Purchase::item_label` / `itemHeading()`). Place réservée 24 h pour envoyer la preuve, puis gardée pendant la vérification ; confirmée sous le seuil ou à la validation ; libérée si le paiement est refusé ou la preuve pas envoyée à temps. `PurchaseManager` traite un supplément sans toucher à l'accès à la formation. **Remboursement** (validé par Joseph) : remboursé si l'élève annule lui-même dans le délai (24 h avant ; `SessionRegistrar::cancelByStudent` remplit `purchases.refund_due_at`) ou si l'école annule la session ; pas remboursé en cas d'absence sans annulation. Portée `Purchase::refundDue()` : une seule liste « Suppléments à rembourser » sur la page admin de la session (motif affiché par `Purchase::refundReason()`), compteur sur la liste des sessions, bouton « Marquer comme remboursé ». Un ancien supplément ne confirme ni ne libère jamais une nouvelle inscription (`purchase_id` comparé). **Étape 8** : aucune commission d'affiliation sur un supplément de session.
- **Cycle de vie** (`App\LiveSessions\SessionManager`) : à la création, l'annonce (avec le lien Meet pour le direct) est publiée et épinglée dans le groupe de la formation (`App\Chat\MessagePins`) ; une modification importante (date, heure, durée, lieu, lien) met l'annonce à jour et prévient les élèves concernés ; une annulation annule les inscriptions, désépingle l'annonce, publie un message d'annulation, prévient les élèves et liste les suppléments à rembourser (bouton « Marquer comme remboursé »). L'annonce est désépinglée après la session.
- **Notifications** (`App\LiveSessions\SessionNotifier`, e-mail `App\Mail\LiveSessionMail`, téléphone `App\Jobs\SendPushNotification`) : rappels la veille et 1 h avant (tous les acheteurs pour le direct, les inscrits pour le présentiel), en respectant les réglages de l'élève (« Rappels des sessions par e-mail » `users.session_email_enabled`, notifications sur téléphone) ; changements et annulations toujours envoyés par e-mail. Cron : `php artisan app:process-live-sessions` toutes les 5 minutes (rappels, places réservées expirées, annonces à désépingler).
- **Heures** (`App\LiveSessions\SessionTime`) : heure de Lomé « (GMT) », même heure au Burkina Faso, heure du Bénin (GMT+1) affichée à côté. Fichier « Ajouter à mon agenda » `App\LiveSessions\CalendarFile` (.ics en UTC).
- **Élève** : `/mon-espace/sessions` et `/mon-espace/sessions/{id}` (lien Meet, bouton « Rejoindre la session » actif 15 min avant via `…/rejoindre`, inscription, paiement du supplément, agenda), carte « Sessions en direct ou à Lomé » sur l'accueil de l'espace élève et sur la page de la formation achetée.
- **Après la session** : feuille de présence imprimable avec cases à cocher (`/admin/sessions/{id}/presence`), bouton admin « Ajouter l'enregistrement comme leçon » (formulaire de leçon pré-rempli dans le dernier module de la formation), historique des sessions passées.
- **Tests** : `tests/Feature/Sessions/`.

## Affiliation (étape 8)

- **Règles** (validées par Joseph, réglables dans `config/affiliate.php`) : tout inscrit peut devenir affilié, même sans achat ; commission de `rate` % (10) sur chaque achat **validé** (formations **et** suppléments de sessions) ; clic valable `cookie_days` jours (30), le dernier lien cliqué compte ; aucune commission sur ses propres achats ; disponible `availability_days` jours (7) après la validation ; retrait minimum `min_withdrawal` (2 000 FCFA), une seule demande en cours ; frais d'envoi Mobile Money déduits du montant retiré (saisis par l'admin). Textes de l'accueil dans `config/site.php` (clé `affiliate`) et question de FAQ : à adapter à la main si les règles changent. Aucune promesse de gains.
- **Modèles** : `Affiliate` (code des liens, conditions acceptées, suspension, coordonnées de retrait `payout_*` : pays, opérateur = clé d'un moyen de paiement de l'étape 4, numéro international, titulaire ; `payout_changed_at` = modification signalée à l'admin), `AffiliateClick` (empreintes HMAC du navigateur et de la connexion, jamais l'IP en clair), `AffiliateCommission` (type `App\Enums\CommissionType` : vente ou déduction négative ; statut `App\Enums\CommissionStatus` : en attente, disponible, payée, annulée ; `affiliate_withdrawal_id` = comprise dans un retrait), `AffiliateWithdrawal` (statut `App\Enums\WithdrawalStatus`, copie des coordonnées, frais, montant reçu, identifiant de transaction, motif du refus). `users.referred_by_affiliate_id` (inscription par un lien), `purchases.affiliate_code` (code du dernier lien cliqué, jamais celui de l'acheteur).
- **Liens** : `?ref=CODE` sur l'accueil ou une page formation. Middleware `TrackAffiliateReferral` (groupe `web`) + `App\Affiliates\ReferralTracker` : cookie `lis_ref` (« CODE|date du clic », la durée est vérifiée côté serveur), cookie `lis_visitor` (identifiant aléatoire), clic compté une fois par personne (même navigateur, ou même connexion et appareil sur 24 h), robots d'aperçu ignorés, redirection vers la même page sans le code. Affilié suspendu ou propre lien : ignoré. Attribution à l'inscription (`CreateNewUser`) et au paiement (`SubmitManualPayment`, formations et suppléments).
- **Commissions** (`App\Affiliates\CommissionManager`) : créées **uniquement** par l'écouteur `CreateAffiliateCommission` sur `PaymentValidated` (jamais sur un accès provisoire) ; annulées par `CancelAffiliateCommission` sur `PaymentRejected` / `PaymentRefunded` (nouvel événement émis par `PurchaseManager::refund`) si pas encore versées (retirées d'un retrait en cours dont le montant est recalculé) ; déjà versées → ligne de déduction négative (solde négatif possible, visible de l'admin). `php artisan app:release-affiliate-commissions` (toutes les heures) les rend disponibles et prévient l'affilié. Solde et statistiques : `App\Affiliates\AffiliateAccount`.
- **Retraits** (`App\Affiliates\WithdrawalManager`) : demande = tout le solde (commissions disponibles et déductions), verrou sur l'affilié ; payé (frais < montant, montant reçu = demandé − frais, commissions « payées ») ; refusé (motif, le montant revient dans le solde). Activation, coordonnées et suspension : `App\Affiliates\AffiliateManager`.
- **Alertes** (`App\Affiliates\AffiliateAlerts`, indices sans blocage) : numéro payeur = numéro WhatsApp ou de retrait de l'affilié, numéro de retrait partagé par plusieurs affiliés, beaucoup d'inscriptions sans achat (`alert_signups_without_purchase`), coordonnées modifiées depuis le dernier retrait payé, solde négatif, affilié suspendu.
- **Élève** : onglet « Affiliation » (`/mon-espace/affiliation`, contrôleur `Student\AffiliateController`, vues `resources/views/site/student/affiliate/`) : activation avec acceptation des conditions, liens (site et chaque formation) avec « Copier », WhatsApp et Facebook (composant `x-site.share-link`), statistiques, commissions (`…/commissions`), coordonnées et retraits (`…/retraits`). **Jamais** le nom, le numéro ni l'e-mail des acheteurs (vérifié par les tests). Règles affichées : `site/partials/affiliate-rules.blade.php`.
- **Admin uniquement** (jamais les modérateurs) : « Retraits à payer » `/admin/affiliation/retraits` (coordonnées, solde, alertes, « Marquer comme payé » avec frais réels et identifiant, « Refuser » avec motif ; compteur `site/partials/admin-withdrawals-link.blade.php`), « Affiliés » `/admin/affiliation/affilies` (statistiques, alertes, suspendre / réactiver), mention de l'affilié et alertes sur « Paiements à vérifier ».
- **Public** : page « Devenez affilié » `/devenir-affilie` (lien dans le pied de page, section de l'accueil, plan du site). CGV article 9 et politique de confidentialité (coordonnées de retrait, suivi des clics, cookies) complétées.
- **E-mails** (file d'attente) : `App\Mail\AffiliateMail` (nouvelle commission, commissions disponibles, retrait payé, retrait refusé ; jamais de donnée de l'acheteur) et `App\Mail\AffiliateAdminMail` (nouvelle demande de retrait, coordonnées modifiées), vues `resources/views/emails/affiliates/`.
- **Tests** : `tests/Feature/Affiliates/`.

## Notes sur l'environnement cloud de Claude

- Dans l'environnement Claude Code web, les téléchargements Composer via l'API GitHub peuvent être refusés (403). Solution qui marche :
  `composer config -g use-github-api false` puis `composer install --prefer-source`.
  Le paquet `phpstan/phpstan` n'existe qu'en archive : le reconstruire depuis son dépôt git avec `git archive` et le placer dans le cache Composer (`~/.cache/composer/files/phpstan/phpstan/<sha1 de l'URL>.zip`).
- `fonts.bunny.net` est bloqué : la police Instrument Sans est donc servie en local via le paquet npm `@fontsource-variable/instrument-sans`. C'est aussi plus rapide pour les visiteurs.
- PHP 8.4 minimum (les dépendances Symfony 8 l'exigent) : sélectionner PHP 8.4 dans le panneau Hostinger.
- Hostinger mutualisé ne dispose pas forcément de Node.js : prévoir à l'étape 11 de compiler les fichiers CSS/JS ailleurs (GitHub Actions) avant le déploiement.
- **À vérifier à l'étape 11** : l'envoi réel d'une vidéo de 50 Mo dans un groupe sur Hostinger. `public/.user.ini` demande `upload_max_filesize = 64M` et `post_max_size = 70M`, mais Hostinger peut imposer ses propres limites : vérifier dans le panneau Hostinger (Avancé > Configuration PHP > Options PHP : `upload_max_filesize`, `post_max_size`, `max_execution_time`, `memory_limit`) et les augmenter si nécessaire, puis refaire l'essai depuis un téléphone.
