# CLAUDE.md : Lomé IA School

Ce fichier donne à Claude le contexte du projet. Le lire avant toute modification.

## La personne qui porte le projet

- N'est **pas développeuse ou développeur** et travaille **uniquement depuis un téléphone**, via Claude Code sur le web.
- **Langue (règle absolue)** : toutes les réponses, tous les résumés et tous les messages destinés à Joseph (porteur du projet) sont rédigés **en français simple, sans exception** : réponses dans la conversation, résumés de fin d'étape, commentaires et descriptions de pull request, messages d'aperçu. Jamais d'anglais, même pour une réponse courte.
- Toujours expliquer simplement, en français, ce qui a été fait et pourquoi.
- Signaler clairement tout ce qu'elle doit faire elle-même : créer un compte, fournir une clé d'API, cliquer sur un bouton dans un tableau de bord, valider une pull request…
- Aucune commande ne peut être lancée de son côté sur un ordinateur : Claude exécute, vérifie et pousse tout.
- Finir chaque étape par un résumé : fait / échoué / à faire de son côté.

## Le produit

Plateforme de vente et de suivi de formations en intelligence artificielle, basée à Lomé (Togo).

- **Achat puis accès immédiat** : l'élève paie et accède tout de suite à la formation.
- **Trois formats** :
  - enregistré : vidéos intégrées (YouTube aujourd'hui) ;
  - en direct : sessions Google Meet ;
  - en présentiel : à Lomé.
- **Groupe de discussion par formation**, réservé aux acheteurs, dans le style de WhatsApp : texte, images, captures d'écran, notes vocales, vidéos courtes, fichiers. Il doit être très professionnel et confortable à utiliser, sur mobile d'abord.
- **Affiliation** : un élève gagne 10 % de chaque vente faite via son lien. Retrait par Mobile Money. Au début, les retraits sont validés manuellement par l'admin.
- **Consultation gratuite** sur réservation.
- **Tableau de bord admin** complet.
- **Paiement** : aujourd'hui, Mobile Money **manuel avec preuve de paiement** (entreprise pas encore certifiée) ; FedaPay sera ajouté plus tard.
- **Exigences** : très professionnel, rapide, pensé mobile en priorité, conçu pour convertir les visiteurs en acheteurs.
- **Langue** : français. **Monnaie** : FCFA (XOF). **Fuseau horaire** : `Africa/Lome` (UTC+0, sans heure d'été).

## Stack technique (imposée)

- Laravel 13, PHP 8.4+ (starter kit officiel Livewire, authentification Fortify).
- Livewire 4 (composants monofichiers dans `resources/views/pages`, préfixe ⚡) + Flux UI + Alpine.js + Tailwind CSS 4 (Vite, via `vite-plus`).
- Base de données : SQLite en développement (`database/database.sqlite`), **MySQL en production**. Tout le code doit rester compatible MySQL.
- Temps réel du chat : Pusher, avec mise à jour régulière automatique (sans WebSocket) si Pusher est absent ou en panne.
- Paiement : Mobile Money manuel avec preuve (étape 4) ; FedaPay plus tard, derrière la notion de moyen de paiement (`App\Enums\PaymentGateway`).
- Hébergement final : Hostinger mutualisé avec SSH. **Pas de processus permanent** : files d'attente et tâches planifiées passent par cron (`schedule:run` chaque minute, `queue:work --stop-when-empty`).
- Fournisseur vidéo **interchangeable** : YouTube maintenant, Bunny.net plus tard.

## Règle sur les contenus (impérative)

- **Ne jamais inventer** de bonus, chiffres, durées, nombres de vidéos ou de leçons, résultats promis, avis, notes ou autres promesses.
- Tout contenu marketing qui n'a pas été fourni par la porteuse du projet doit lui être **signalé explicitement** (liste claire, formation par formation) avant d'être considéré comme validé.
- Les textes décrivent **ce que l'élève apprend à faire**, jamais un résultat garanti (revenus, clients, ventes, gain de temps, popularité). Le ton reste vendeur et dynamique.

## Conventions de code

- **Nommage** : code (classes, méthodes, variables, tables, colonnes) en anglais ; tout texte visible par l'utilisateur en français.
- **Textes d'interface** : le starter kit utilise des clés anglaises traduites dans `lang/fr.json`. Garder ce mécanisme pour ces écrans ; pour les nouveaux écrans, le français peut être écrit directement dans les vues Blade. Messages de validation : `lang/fr/validation.php`.
- **Style** : suivre le style existant ; `composer lint` (Pint) avant chaque commit.
- **Montants** : en FCFA, stockés en **entiers** (le XOF n'a pas de décimales). Jamais de float pour l'argent. Affichage : `25 000 FCFA`.
- **Dates** : l'application tourne en `Africa/Lome`. Affichage en français (`translatedFormat`).
- **Compatibilité MySQL** : uniquement via les migrations et le query builder / Eloquent. Pas de SQL brut propre à SQLite. Attention aux types (`enum` natifs à éviter, préférer `string` + enum PHP), aux index uniques et aux clés étrangères.
- **Services externes** derrière une interface (ex. `VideoProvider` avec une implémentation `YouTubeVideoProvider`), choisis par la configuration, pour pouvoir changer de fournisseur sans toucher au reste du code.
- **Clés et secrets** uniquement dans `.env` (jamais commités) ; documenter chaque nouvelle variable dans `.env.example`.
- **Mobile d'abord** : concevoir chaque écran pour un petit écran, puis l'agrandir.
- **Tâches longues** (e-mails, traitements de médias) : en file d'attente (driver `database`), jamais pendant la requête.
- **Tests** : un test de fonctionnalité (PHPUnit) pour chaque parcours important (achat, accès, affiliation, retrait).
- **Champs de lien de l'admin** (lien Google Meet de la consultation et des sessions, liens YouTube et Google Drive des leçons et ressources, vidéo de la page Entreprises, vidéo des témoignages, carte et réseaux sociaux) : toujours **nettoyés avant la vérification** par `App\Support\PastedLink` (`PastedLink::cleanRequest($request, [...])` dans le contrôleur ou `prepareForValidation()` du FormRequest) : caractères invisibles (espace insécable, largeur nulle…) et espaces retirés, lien extrait d'un texte plus long (« Rejoindre avec Google Meet : https://… »), majuscules du clavier retirées de « https:// » et du nom de domaine (jamais du chemin : identifiants YouTube et Drive), « https:// » ajouté s'il manque. `GoogleMeet::normalize`, `YouTube::id`, `GoogleDrive::fileId` nettoient aussi. Message d'erreur qui montre la forme attendue (`GoogleMeet::invalidMessage()`, `YouTube::invalidMessage()`). Dans les vues, **jamais `type="url"`** (le navigateur refuserait lui-même un lien sans https ou entouré de texte) : `type="text" inputmode="url" autocapitalize="none" autocorrect="off" spellcheck="false"` (fait automatiquement par `x-admin.field type="url"`). Même nettoyage côté navigateur pour l'aperçu vidéo (`cleanPastedLink` dans `site.js`). Tests : `tests/Unit/PastedLinkTest.php` et un test par écran.

## Comptes, rôles et accès

- **Inscription** : nom, numéro WhatsApp (obligatoire, unique, stocké au format international complet via `App\Support\PhoneNumber`, règle `App\Rules\WhatsAppNumber`). `PhoneNumber::PLANS` donne, par pays, la longueur du numéro et si le 0 initial est un simple préfixe national (France, Ghana, Nigeria…) ; en Afrique de l'Ouest il fait généralement partie du numéro et n'est **jamais retiré** (Bénin : 10 chiffres commençant par 01, un ancien numéro à 8 chiffres reçoit 01 devant ; Burkina Faso : 8 chiffres, ex. +226 07 27 63 81). Même règle pour le profil et le numéro payeur des paiements. Réparer des numéros enregistrés par l'ancienne normalisation (0 perdu) : `php artisan app:fix-phone-numbers [--dry-run]` (ne crée jamais de doublon), e-mail, mot de passe (pas de confirmation, bouton « Afficher »), case facultative **non cochée par défaut** « Je souhaite être informé(e) des nouvelles formations » (colonne `users.wants_newsletter`, modifiable dans le profil, composant `x-site.newsletter-checkbox`). N'envoyer d'annonces qu'aux élèves dont `wants_newsletter` est vrai. Pages d'authentification au design du site : `resources/views/site/auth/`.
- **Rôles** : `App\Enums\UserRole` (élève, modérateur, admin), colonne `users.role` non modifiable par formulaire. Créer ou promouvoir un admin : `php artisan app:make-admin email@exemple.com` (le mot de passe est demandé au clavier, jamais écrit dans le code). Zone admin protégée par le middleware `admin` et la permission `access-admin` (préfixe `/admin`). **Double authentification obligatoire** pour l'admin et les modérateurs (middleware `staff-2fa`, `App\Http\Middleware\RequireStaffTwoFactor`) : sans elle, ils sont envoyés vers « Sécurité du compte ». Dans les tests, la fabrique donne automatiquement la double authentification à l'équipe (état `withoutTwoFactor()` pour tester son absence).
- **Inscriptions aux formations** : table `enrollments` (élève, formation, `source` = `purchase` ou `admin`, `granted_at`). Règle d'accès au contenu : `App\Policies\FormationPolicy::access` (élève inscrit ou admin), à utiliser avec `can:access,formation` aux étapes 5 et 6. Donner ou retirer un accès : `php artisan app:grant-access email slug [--revoke]`.
- **Retour après connexion** : un visiteur qui passe par `/commande/{slug}` y revient automatiquement après inscription ou connexion (URL « intended » de la session).
- **Espace élève** « Mon espace » (`/mon-espace`) : vues `resources/views/site/student/`, variante `student` du layout du site (barre de navigation en bas sur téléphone). Profil et photo : `/mon-espace/profil` (photo recadrée en 320 × 320 par `App\Services\AvatarProcessor`, disque `public` : nécessite `php artisan storage:link` sur le serveur). Sécurité du compte (mot de passe, double authentification, passkeys) : `/mon-espace/securite` (`App\Http\Controllers\Student\SecurityController`), via les routes de Fortify et de Laravel Passkeys.
- **Confirmation de l'adresse e-mail** (`App\Accounts\EmailConfirmation`, table `email_verifications`, modèle `EmailVerification`, `users.email_verified_at`, `User::hasConfirmedEmail()`) : juste après l'inscription (écouteur `SendEmailConfirmationCode` sur `Registered`), e-mail `App\Mail\EmailConfirmationMail` avec un **code à 6 chiffres** et un **bouton** (`/confirmer-email/{jeton}`, fonctionne même sans être connecté), valables **30 minutes**, **usage unique** ; un nouvel envoi annule l'ancien code et l'ancien lien. Code et jeton jamais en clair en base (empreintes `Hash` et SHA-256) ; l'e-mail part **juste après la réponse** (`defer()`), jamais par la file d'attente (le code n'est jamais écrit dans la table `jobs`). Force brute : **5 codes erronés → code annulé et saisie bloquée 15 minutes**. Retour automatique à la page d'origine (récapitulatif de commande, paiement du supplément, retraits : paramètre `retour` ou URL « intended »). Nouvelle adresse dans le profil : à confirmer de la même façon. Admin : statut sur la fiche élève, bouton « Confirmer l'email manuellement » (`admin.students.confirm-email`, journal `AdminAction::EmailConfirmed`), filtre « E-mail non confirmé ». Politique de confidentialité complétée. Tests : `tests/Feature/Auth/EmailConfirmationTest.php`.
- **E-mails** : `App\Mail\WelcomeMail` (file d'attente) envoyé à l'inscription par `App\Listeners\SendWelcomeEmail`. En local, `MAIL_MAILER=log` : les e-mails sont écrits dans `storage/logs/laravel.log` quand la file est traitée (`php artisan queue:work --stop-when-empty`).

## Paiements (étape 4 : Mobile Money manuel avec preuve)

- **Configuration** (valeurs de départ dans `config/site.php`, clé `payments` ; modifiables depuis l'étape 10 dans l'admin, « Réglages du site > Moyens de paiement » et « Seuils et délais ») : seuil de vérification (`$verificationThreshold` en haut du fichier, 50 000 FCFA), pays (Togo, Burkina Faso, Bénin, avec la mention du représentant), numéros Mobile Money (nom exact, numéro, bénéficiaire, couleur de pastille, `enabled`), étapes affichées, mention des frais, taille maximale de la capture, e-mail de l'admin. - **Parcours** : `/commande/{slug}` (choix du pays puis du moyen, numéro + « Copier », bénéficiaire, montant exact, étapes) puis formulaire de preuve (`POST /commande/{slug}/paiement`, `App\Http\Requests\StorePaymentProofRequest`). Traitement : `App\Actions\Payments\SubmitManualPayment`.
- **Contrôles automatiques** : formation déjà possédée (accès ou achat provisoire/validé), un seul paiement non vérifié à la fois par élève, identifiant de transaction jamais utilisé (normalisé : sans espaces, en majuscules, index unique), même capture jamais envoyée (empreinte SHA-256 du fichier envoyé, index unique). Échec : message clair, aucun accès, capture supprimée.
- **Accès** : prix < seuil → statut « accès provisoire » et accès immédiat ; prix ≥ seuil → « en attente de validation », aucun accès avant validation. - **Table `purchases`** (`App\Models\Purchase`, statuts `App\Enums\PurchaseStatus` : provisoire, en attente, validé, refusé, remboursé) : élève, formation, montant, passerelle (`gateway`), moyen de paiement (clé + copie du nom, du numéro et du bénéficiaire), pays, numéro payeur, nom de l'expéditeur, identifiant de transaction, capture (`proof_path`), empreinte, admin et date de vérification, motif du refus. - **Captures** : disque privé `payment_proofs` (`storage/app/private/payment-proofs`, jamais public), réduites à 1600 px et compressées en JPEG (`App\Payments\ProofImageProcessor`). Lecture uniquement par l'élève propriétaire ou l'admin (`App\Policies\PurchasePolicy`, `App\Http\Controllers\PurchaseProofController`, en-têtes `no-store`). À sauvegarder avec la base (étape 11).
- **Cycle de vie** : `App\Services\PurchaseManager` (commun à tous les moyens de paiement) : `grantAccess`, `validate`, `reject` (retire l'accès immédiatement, option de blocage du compte), `refund`, `block`/`unblock`. Compte bloqué (`users.blocked_at`) : connexion refusée (`FortifyServiceProvider`) et session fermée (middleware `LogoutBlockedUser`).
- **Événements** : `FormationAccessGranted` (branché : ajout au groupe), `FormationAccessRevoked` (branché : retrait du groupe), `AccountBlocked` / `AccountUnblocked` (branchés : retrait de tous les groupes / retour), `PaymentValidated` (étape 8 : commission d'affiliation **uniquement ici**, jamais sur un accès provisoire), `PaymentRejected`, `PaymentSubmitted`.
- **E-mails** (file d'attente, dans le journal en local) : `PaymentProofReceivedMail` (élève), `NewPaymentToVerifyMail` (admin, adresse `payments.admin_email`), `PaymentValidatedMail` (avec lien vers le reçu), `PaymentRejectedMail` (avec le motif). Gabarit commun : `resources/views/emails/layout.blade.php`.
- **Élève** : « Mes achats » `/mon-espace/achats` (statuts), suivi d'un achat `/mon-espace/achats/{id}` (sert de confirmation), reçu imprimable `/mon-espace/achats/{id}/recu` (paiement validé uniquement ; page autonome claire, `color-scheme: only light`). Mention « accès provisoire » sur les formations concernées.
- **Admin** : « Paiements à vérifier » `/admin/paiements` (provisoires et en attente, plus récents en haut, capture en grand, détails, signaux d'alerte `App\Services\PaymentAlerts`, rappel « À confirmer avec le représentant » pour le Burkina Faso et le Bénin, boutons Valider / Refuser avec motif et blocage du compte, dernières décisions). Compteur dans le menu admin (`site/partials/admin-payments-link.blade.php`).

## Sessions ponctuelles en direct et en présentiel (étape 7)

- **Principe** : toutes les formations sont enregistrées ; l'admin ou un modérateur annonce de temps en temps une session pour une formation. **Aucune session ni date n'est inventée** : tout est créé depuis l'écran « Sessions » (`/admin/sessions`, permission `manage-sessions` = admin et modérateurs).
- **Modèles** : `LiveSession` (formation, type `App\Enums\SessionFormat` en direct / présentiel, titre et description facultatifs, `starts_at` à l'heure de Lomé, `duration_minutes`, `ends_at` calculé, lien Google Meet vérifié par `App\Support\GoogleMeet`, lieu pré-rempli, places, tarif `App\Enums\SessionPriceType` inclus / supplément en FCFA, annulation, annonce du groupe, rappels envoyés) et `LiveSessionRegistration` (statut `App\Enums\RegistrationStatus` : inscrit, place réservée, liste d'attente, annulée ; paiement, présence). Réglages : `config/live_sessions.php` (lieu par défaut, délai d'annulation 24 h, bouton « Rejoindre » 15 min avant, rappels veille et 1 h, délai de 24 h pour payer un supplément, heure du Bénin).
- **Qui voit quoi** (`App\Policies\LiveSessionPolicy`) : élèves ayant accès à la formation (accès provisoire compris) et équipe. Le lien Google Meet n'est **jamais** affiché aux non-acheteurs ni sur les pages publiques (page formation « Prochaine session » et accueil « Prochaines sessions » via `x-site.session-summary`, sans lien).
- **Présentiel** (`App\LiveSessions\SessionRegistrar`) : inscription obligatoire, places limitées (verrou pour ne jamais dépasser), liste d'attente ; une place libérée va automatiquement à la première personne en attente, prévenue par e-mail et notification. Annulation par l'élève jusqu'au délai. Accès retiré ou compte bloqué → inscriptions annulées (écouteur `CancelSessionRegistrationsOnAccessLoss`).
- **Supplément** : même paiement Mobile Money avec preuve que les formations (`SubmitManualPayment` avec `$session`, `purchases.live_session_id`, mêmes contrôles, même seuil, même page « Paiements à vérifier », reçu dans « Mes achats », libellés `Purchase::item_label` / `itemHeading()`). Portée `Purchase::refundDue()` : une seule liste « Suppléments à rembourser » sur la page admin de la session (motif affiché par `Purchase::refundReason()`), compteur sur la liste des sessions, bouton « Marquer comme remboursé ». Un ancien supplément ne confirme ni ne libère jamais une nouvelle inscription (`purchase_id` comparé). **Étape 8** : aucune commission d'affiliation sur un supplément de session.
- **Cycle de vie** (`App\LiveSessions\SessionManager`) : à la création, l'annonce (avec le lien Meet pour le direct) est publiée et épinglée dans le groupe de la formation (`App\Chat\MessagePins`) ; une modification importante (date, heure, durée, lieu, lien) met l'annonce à jour et prévient les élèves concernés ; une annulation annule les inscriptions, désépingle l'annonce, publie un message d'annulation, prévient les élèves et liste les suppléments à rembourser (bouton « Marquer comme remboursé »). L'annonce est désépinglée après la session.
- **Notifications** (`App\LiveSessions\SessionNotifier`, e-mail `App\Mail\LiveSessionMail`, téléphone `App\Jobs\SendPushNotification`) : rappels la veille et 1 h avant (tous les acheteurs pour le direct, les inscrits pour le présentiel), en respectant les réglages de l'élève (« Rappels des sessions par e-mail » `users.session_email_enabled`, notifications sur téléphone) ; changements et annulations toujours envoyés par e-mail. Cron : `php artisan app:process-live-sessions` toutes les 5 minutes (rappels, places réservées expirées, annonces à désépingler).
- **Heures** (`App\LiveSessions\SessionTime`) : heure de Lomé « (GMT) », même heure au Burkina Faso, heure du Bénin (GMT+1) affichée à côté. Fichier « Ajouter à mon agenda » `App\LiveSessions\CalendarFile` (.ics en UTC) et bouton **« Ajouter à Google Agenda »** (`CalendarFile::googleUrl()`, lien `calendar.google.com/calendar/render` construit par `App\Support\GoogleCalendar` : titre, heures de Lomé, durée, description, lieu, fuseau `ctz=Africa/Lome`) ; les deux boutons : partiel `site/partials/calendar-buttons.blade.php` (aussi sur la page de gestion de la consultation et dans son e-mail, `ConsultationCalendar::googleUrl()`).
- **Élève** : `/mon-espace/sessions` et `/mon-espace/sessions/{id}` (lien Meet, bouton « Rejoindre la session » actif 15 min avant via `…/rejoindre`, inscription, paiement du supplément, agenda), carte « Sessions en direct ou à Lomé » sur l'accueil de l'espace élève et sur la page de la formation achetée.
- **Après la session** : feuille de présence imprimable avec cases à cocher (`/admin/sessions/{id}/presence`), bouton admin « Ajouter l'enregistrement comme leçon » (formulaire de leçon pré-rempli dans le dernier module de la formation), historique des sessions passées.

## Déploiement Laravel Cloud (temporaire)

- **État** : en ligne sur **https://lomeiaschool.laravel.cloud**, utilisé **avec de vrais élèves et de vrais paiements** depuis fin septembre 2026, en attendant Hostinger. Toute intervention doit donc préserver les données (jamais de base vidée, jamais de `db:seed`, jamais de suppression de fichiers des buckets).
- **But** : mettre le site en ligne **temporairement** sur Laravel Cloud (offre Starter, crédit gratuit de 5 $ par mois), en attendant Hostinger, qui reste l'hébergement **définitif**. Tout se règle par les **variables d'environnement** (`.env` sur Hostinger, onglet « Environment variables » sur Laravel Cloud) : **aucune modification du code** pour passer de l'un à l'autre. Sans ces variables, le comportement est exactement celui de Hostinger.
- **Fichiers envoyés** (`App\Support\FileStorage`, appelé au démarrage par `AppServiceProvider`) : `PRIVATE_FILES_DISK` et `PUBLIC_FILES_DISK` (défaut `local` = dossiers du serveur, Hostinger). Sur Laravel Cloud, le disque de chaque bucket est ajouté automatiquement par le framework (variable `LARAVEL_CLOUD_DISK_CONFIG`, `Illuminate\Foundation\CloudBootstrapper`) sous le nom choisi dans le tableau de bord : bucket **privé** nommé `prive`, bucket **public** nommé `publics`. Les disques privés (`payment_proofs`, `lesson_resources`, `chat_media`) deviennent des sous-dossiers du bucket privé (driver `scoped`, préfixes `payment-proofs/`, `lesson-resources/`, `chat/`) ; le disque `public` (photos de profil, images des formations, témoignages, logo et icônes envoyés) pointe vers le bucket public. Autre stockage compatible S3 : `s3` + variables `AWS_*`. Paquets `league/flysystem-aws-s3-v3` et `league/flysystem-path-prefixing` (sans effet sur Hostinger).
- **Fichiers privés jamais publics** : droits vérifiés par l'application (mêmes politiques qu'avant), puis `FileStorage::privateResponse()` : sur le serveur, réponse directe (lecture par morceaux) ; sur stockage objet, **redirection vers un lien temporaire signé** (5 min ; 30 min pour les fichiers des groupes, pour reprendre une note vocale ou une vidéo en pause), en-têtes `no-store`. Sur un stockage objet, l'existence des fichiers publics n'est pas vérifiée à chaque affichage (`FileStorage::publicUrl`, évite une requête réseau par image). Jeu d'icônes envoyé depuis l'admin : créé dans `storage/app/tmp`, puis copié sur le disque `public`. Image de partage envoyée : redirection vers son adresse publique. Pas de `visibility` sur le disque public (Cloudflare R2 la refuse : c'est le bucket public qui rend les fichiers visibles). Tests : `tests/Feature/Deployment/ObjectStorageTest.php`, `tests/Feature/Chat/ObjectStorageAttachmentTest.php`.
